MapReduce-Reloaded

In active development · big data & distributed systems · Go & Python

A from-scratch rebuild of Google’s MapReduce, as described by Dean and Ghemawat in MapReduce: Simplified Data Processing on Large Clusters⁠ (OSDI 2004). Go is the main implementation. Python is a second implementation of the shared contract and of single-machine mode, so the two can be checked against each other byte for byte.

View the code

Work in progress. Reviewed on 11 November 2026 against revision def9c62⁠. Object storage, compression, benchmarks, the demo script and the final report are now built. Python workers and full cross-language interoperability remain stretch work. The evaluation below is reported by the source repository, not rerun for this page.

At a glance

24 items in the paper mapping: F1–F23 plus the F24 performance experiments

4 one-CPU worker containers on the course VM, not four independent machines

3.8× reported word-count speedup from one to four workers on 1 GiB inputs

The problem

MapReduce is the paper that made large-scale data processing ordinary. You write a map function and a reduce function, and the system handles splitting the input, scheduling thousands of tasks, moving data between machines and surviving the machines that fail along the way. Spark, Hadoop and most modern batch systems descend from it.

I wanted to understand those guarantees by building them, not by reading about them. The aim is a faithful rebuild: every feature in the paper, each with a test that proves it works, then extended with what a 2026 system would use instead of 2004 infrastructure.

Approach

The diagram shows the core task and shuffle path only. It does not attempt to draw the S3 backend, alternative Python coordinator or benchmark harness.

A single-machine oracle first. The first working version runs the whole job in one process (mr run -local). Every later version, distributed or fault tolerant, must produce exactly the same output files. The tests check each version against it.

One contract, two languages. Go and Python share a gRPC and protobuf message contract, a documented on-disk record format with a checksum on every block, and a fixed FNV-1a partition hash implemented in both languages. Language-specific hash behavior is not the contract: shared test vectors and golden files hold both implementations to the same bytes for uncompressed jobs.

Small, reviewable steps. One issue and one pull request per change, 199 merged by 10 November 2026, and 22 design records. Branch protection holds main until six CircleCI checks pass, and CodeRabbit and CodeAnt review every pull request; several real bugs were found in review, not by the tests.

What I built

  • The programming model and the data path (§2–§4.4). Input splitting on record boundaries, partitioning by hash(key) mod R, a combiner, an external merge sort for data larger than memory, pluggable input and output formats, and atomic commits, so a half-written output file is never visible.
  • A distributed cluster (§3.1–§3.2). A coordinator keeps the task table and the location of every intermediate file. Workers ask it for tasks over gRPC, map tasks write R partition files and serve them, and reducers stream their partition from every map task.
  • Fault tolerance (§3.3, §3.6, §4.6, §4.9).
    • Workers send heartbeats. A worker that misses three is declared dead, and its finished map tasks run again, because their output was on its disk.
    • The coordinator logs every decision to a write-ahead log and resumes the job after a restart. The 2004 implementation aborted the job instead.
    • Backup copies of the last slow tasks run near the end of a job, and the first copy to finish wins.
    • A record that crashes user code twice is skipped on the next attempt.
    • Counters are counted only from the winning attempt of each task, so re-run tasks do not double-count.
  • Locality and status (§3.4, §4.8). The scheduler prefers to run a map task on the host that holds its input. The coordinator serves a status page, the coordinator and workers export Prometheus metrics, an optional monitoring profile adds Prometheus and a Grafana dashboard, and logs can be written as structured JSON.
  • The paper’s example programs (§2.3, §5). Grep, word count, URL access frequency, reverse web-link graph, term vectors, inverted index and distributed sort, each with a test.
  • A Docker Compose cluster. One coordinator and four workers, with Prometheus and Grafana as an optional profile, and a memory limit on each service so the whole cluster fits on one 8 GB virtual machine. An end-to-end script checks the cluster’s output against the oracle.
  • A six-minute demo. A script, mirrored by a notebook that checks each step with an assert, kills a worker and restarts the coordinator mid-sort.
  • Storage, compression and user jobs. S3-compatible storage with object-store commit semantics, zstd and Snappy codecs, and Go job files interpreted by workers. A Python coordinator can run with Go workers; a Python worker is not implemented.

What chaos testing found

The chaos test runs word count while, at random moments, workers die, new ones join, workers stall for 50–250 ms and the coordinator restarts from its log. A run passes only if the output files and the counters equal single-machine mode. Each run’s choices come from a seed, so a failure can be replayed.

Its first runs failed on seed 7. The output held an extra _temporary directory: a reduce attempt that had already lost, to a backup copy or because its worker was declared dead, kept running and recreated the directory after the job had cleaned it up. Now the job creates that directory when it starts, and attempts never do. An attempt that runs after the job has finished fails and leaves nothing behind.

The original test runs in one process, so a “dead” worker behaves like a machine cut off from the network, not one that lost power. The repository now also has a seeded make chaos driver for container kills, pauses and coordinator crashes in Compose. Dropped-packet fault injection remains out of scope.

What is planned

Python workers and a complete Go/Python interoperability matrix, coordinator high availability, skew handling and Parquet input remain stretch goals. LATE-style speculation is built as an opt-in mode, but its E7 evaluation has not been run; there is no measured claim that it is faster.

What I’m learning

  • Build the oracle first. Once a simple version defines the right answer, every harder version is a test against it, not a judgement call.
  • Write the contract down before the code. The hand-written hash exists because both languages’ built-in hashes would have sent the same key to different reducers without any error.
  • Random fault injection finds bugs that one-failure-at-a-time tests miss. The seed 7 bug appeared only when a losing attempt outlived the job’s cleanup.
